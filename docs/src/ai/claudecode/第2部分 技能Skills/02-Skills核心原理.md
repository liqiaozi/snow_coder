> Skills 的核心原理就是"按需加载" — 先亮名片，再看简介，最后翻资料。绝不一次把所有东西都塞进对话.


# 一、已有知识的痛点

假设你给 Claude 装了 20 个 Skill，每个 Skill 包含 5000 Token 的指令和若干参考文档。如果全部加载：

```text
20 个 Skill × 5000 Token = 100,000 Token
一个对话窗口直接撑爆，什么都干不了。
```

渐进式披露就是为了解决这个问题而设计的。


# 二、三层披露架构

![](../../../assets/20260512190252_N4vJnO.png)

| 层级              | 内容组成                    | 加载时机  | Token消耗 | 用途 |
|-----------------|-------------------------|-------|---------|----|
| Level1<br/>元数据层 | YAML元数据中的name和description | 会话启动时 |   约 50-100 tokens      |  快速判断 Skill 相关性  |
| Level2<br/>指令层  |     完整的 SKILL.md 文件     |  任务匹配时     |  通常 < 5000 tokens       |  提供详细的使用指导  |
| Level3<br/>资源层       |      脚本、文档、模板等资源文件                   |  需加载     |  无固定限制       |  提供执行所需的实际资源  |

> Level 1：元数据（始终加载）

元数据就像是 Skill 的“名片”，里面有名称（name）和描述（description），使用 YAML 格式定义。

Claude 在启动的时候，会把所有已经安装的 Skill 的元数据都加载进来，这样它就能知道每个 Skill 有什么用、什么时候该用。


> Level 2：指令层（触发时加载）

用户的请求和 Skills 元数据里的描述相符时，Claude 会用 bash 指令读取这份文档，把内容加载到上下文里。

这种“触发式加载”能保证只有相关的详细指令才会消耗 Token。


> Level 3：资源层（执行时按需加载）

脚本、参考文档、模板文件在此层级：
* 脚本（scripts/）：通过 Bash 执行，脚本代码本身不进入 Token 上下文
* 参考文档（references/）：通过 Read 读取，按需加载，用完可丢弃
* 模板/资源（assets/）：读取后填充使用
