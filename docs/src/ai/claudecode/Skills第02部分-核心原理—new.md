# Skills 核心原理：渐进式披露机制

> **一句话理解**：Skills 的核心原理就是"按需加载" — 先亮名片，再看简介，最后翻资料。绝不一次把所有东西都塞进对话。

---

## 一、已有知识的痛点

假设你给 Claude 装了 20 个 Skill，每个 Skill 包含 5000 Token 的指令和若干参考文档。如果全部加载：

```
20 个 Skill × 5000 Token = 100,000 Token
一个对话窗口直接撑爆，什么都干不了。
```

**渐进式披露（Progressive Disclosure）** 就是为了解决这个问题而设计的。

---

## 二、三层披露架构

```
┌─────────────────────────────────────────────────────────┐
│                   渐进式披露架构                           │
├─────────┬──────────────────┬───────────┬────────────────┤
│   层级   │     内容组成       │   加载时机  │   Token 开销    │
├─────────┼──────────────────┼───────────┼────────────────┤
│ Level 1 │ name +           │ 会话启动时  │  ~50-100 Token │
│  元数据层 │ description      │ 立即加载   │  (极轻量)       │
├─────────┼──────────────────┼───────────┼────────────────┤
│ Level 2 │ SKILL.md 正文     │ 任务匹配时  │  <5000 Token   │
│  指令层   │ (工作流/规则/格式)  │ 按需加载    │                │
├─────────┼──────────────────┼───────────┼────────────────┤
│ Level 3 │ scripts/         │ 执行时需要  │  无固定上限      │
│  资源层   │ references/      │ 按需读取   │  (脚本不占上下文) │
│         │ assets/          │           │                │
└─────────┴──────────────────┴───────────┴────────────────┘
```

### Level 1：元数据层（始终加载）

元数据是 Skill 的**名片** — 只有 `name` 和 `description` 两个字段。

- 加载时机：Claude Code 启动时**立即加载所有已安装 Skill 的元数据**
- 数据量：每个 Skill 约 50~100 Token，装 50 个也才 5000 Token
- 作用：Claude 扫描元数据，建立一个"能力索引表"，知道每个 Skill 能干什么

```
Claude 内存中的"能力索引"大致长这样：

┌────────────────────────────────────────┐
│ code-reviewer  → "审查 Go/Python 代码"  │
│ title-generator → "生成公众号标题"       │
│ pdf-extractor  → "提取 PDF 文档信息"    │
│ api-doc-gen    → "生成 API 接口文档"     │
│ ...                                      │
└────────────────────────────────────────┘
```

### Level 2：指令层（触发时加载）

当用户的请求命中某个 Skill 的描述关键词时：

1. Claude 用 `Read` 工具读取该 Skill 的 `SKILL.md` 完整文件
2. Markdown Body（工作流程、规则、格式要求）被加载到上下文
3. 整个过程对用户**透明** — 你不需要关心加载细节

**关键特性**：只有**匹配到的 Skill** 的指令层才会加载，其他 Skill 仍停留在元数据层。

### Level 3：资源层（执行时按需加载）

脚本、参考文档、模板等资源在此层级：

- **脚本**（`scripts/`）：通过 Bash 执行，**脚本代码本身不进入 Token 上下文**
- **参考文档**（`references/`）：通过 Read 读取，按需加载，用完可丢弃
- **模板/资源**（`assets/`）：读取后填充使用

## 三、渐进式披露工作流程

```
用户提问: "帮我 review 这段 Go 代码"
                    │
                    ▼
┌─────────────────────────────────────┐
│  1. 初始发现                         │
│  Claude 扫描所有 Skill 的元数据       │
│  找到 name + description             │
└─────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────┐
│  2. 相关性评估                       │
│  "code-reviewer" 的 description：    │
│  "审查 Go/Python 代码"...            │
│  → 匹配命中！                        │
└─────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────┐
│  3. 指令加载（Level 2）              │
│  Read → SKILL.md（~3000 Token）     │
│  Claude 获得：                      │
│  • 审查流程：5 个步骤                │
│  • 检查清单：20 项                   │
│  • 输出格式：结构化报告               │
└─────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────┐
│  4. 资源按需加载（Level 3）          │
│  Read → references/go-standards.md  │
│  （只在需要时才读取）                  │
└─────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────┐
│  5. 结果整合                         │
│  • 应用审查规则                      │
│  • 格式化输出                        │
│  • 返回最终审查报告                   │
└─────────────────────────────────────┘
```

## 四、为什么 Token 开销很低？

以一个"Go 代码审查"Skill 为例，对比两种方式：

| 阶段 | 加载了什么 | Token 开销 |
|------|-----------|------------|
| 会话启动 | name + description | ~80 Token |
| 用户请求 | 自动匹配（零消耗） | 0 Token |
| 匹配后 | 加载 SKILL.md 正文 | ~3000 Token |
| 执行中 | 按需读取参考文档 | ~1500 Token |
| **总计** | | **~4580 Token** |

**没有渐进式披露的话**：20 个 Skill × 5000 Token = 100,000 Token → 什么都不用做了。

## 五、渐进式披露的三个核心收益

| 收益 | 说明 |
|------|------|
| **启动即用** | 可以安装 50+ 个 Skill，启动开销 ≈ 0 |
| **按需付费** | 只有命中的 Skill 才消耗 Token，没命中的只占 ~80 Token |
| **深度无限** | 脚本执行不占上下文，参考文档按需读取。Skill 可以做得很"厚"而成本很低 |

## 六、给你的架构启示

```
"轻"在前面，"重"在后面
   ↓
   description → 精准 hook
   SKILL.md    → 流程 + 规则
   scripts/    → 复杂逻辑
   references/ → 按需查阅
```

理解了这个原理，你就明白了 Skills 为什么能够：
- **装得多**：装 50 个 Skill 和装 1 个的开销差别不大
- **能力强**：因为有脚本支持，可以做真正的代码执行而不仅仅是"纸上谈兵"
- **按需付费**：Token 只花在刀刃上

---

> **一句话总结**：渐进式披露 = 先亮身份证 → 看匹配了 → 再掏工作手册 → 干活时翻工具箱。每一步都刚刚好。
